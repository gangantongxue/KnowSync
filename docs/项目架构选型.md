# KnowSync 项目架构选型

> 本文档记录 KnowSync 项目的技术选型理由与架构决策，以便后续开发者和维护者理解设计意图。

## 一、整体架构：微服务架构

### 决策

选择 **微服务架构**，按业务领域拆分为 5 个后端服务 + 1 个 HTTP 网关 + 1 个前端。

### 理由

1. **业务边界清晰**：用户认证、知识库管理、AI 对话、社交聊天是四个独立的业务域，耦合度低，天然适合微服务拆分
2. **独立扩展**：AI 服务是计算密集型（LLM 推理 + 向量化），需要独立扩缩容；其他服务 I/O 密集，资源需求不同
3. **独立迭代**：各服务可由不同团队并行开发，互不阻塞
4. **容错隔离**：AI 服务依赖外部 API（DeepSeek、SiliconFlow），可能因网络或限流故障，隔离后可避免雪崩

### 代价

- 引入服务间网络开销（gRPC 延迟约 1-3ms，可接受）
- 需要额外处理分布式事务（本项目尽量避免，使用最终一致性）
- 部署和运维复杂度增加（通过 Docker Compose 降低）

---

## 二、服务间通信：gRPC

### 决策

服务间通信统一使用 **gRPC**，使用 Protocol Buffers 定义接口契约。

### 备选方案对比

| 特性 | gRPC（选用） | RESTful HTTP | RabbitMQ |
|------|-------------|-------------|----------|
| **协议** | HTTP/2 + Protobuf | HTTP/1.1 + JSON | AMQP |
| **性能** | 高（二进制序列化） | 中（文本 JSON） | 中 |
| **类型安全** | 强（代码生成） | 弱（手动序列化） | 弱 |
| **流式支持** | 原生 Server/Client/Bidi Streaming | 需 SSE/WebSocket | 需额外实现 |
| **工具链** | Protobuf 编译器 + 代码生成 | OpenAPI/Swagger | 无 |

### 理由

1. **性能优势**：Protobuf 二进制序列化比 JSON 小 3-10 倍，快 10-100 倍，适合高频服务调用
2. **强类型契约**：`.proto` 文件生成 Go 代码，编译期即可发现接口不匹配问题
3. **流式 RPC**：AI 对话需要服务端流式返回（SSE），gRPC Server Streaming 天然支持
4. **网关层隔离**：对外暴露 HTTP（通过 Hertz），对内使用 gRPC，网关负责协议转换

---

## 三、HTTP 网关：CloudWeGo Hertz

### 决策

选择 **Hertz** 作为 HTTP 网关框架。

### 备选方案对比

| 特性 | Hertz（选用） | Gin | Echo | Fiber |
|------|-------------|-----|------|-------|
| **性能** | 极高（Netpoll） | 高 | 高 | 极高 |
| **社区** | 中（国内活跃） | 极大 | 大 | 大 |
| **中间件生态** | 中 | 丰富 | 丰富 | 丰富 |
| **与 Eino 集成** | 好（同属 CloudWeGo） | 无 | 无 | 无 |
| **学习曲线** | 中 | 低 | 低 | 低 |

### 理由

1. **CloudWeGo 生态**：与 Eino（AI 编排框架）同属字节跳动 CloudWeGo 开源生态，未来可统一技术栈
2. **高性能**：基于 Netpoll 网络库，吞吐量优于 Gin 和 Echo（参考 CloudWeGo 官方基准测试）
3. **足够的生态**：核心中间件（CORS、JWT、限流）均有成熟实现，满足网关需求
4. **注意**：本项目网关不包含业务逻辑（仅转换 HTTP → gRPC），因此框架差异影响有限

---

## 四、AI 编排框架：CloudWeGo Eino

### 决策

选择 **Eino** 作为 LLM 编排框架，对接 DeepSeek API。

### 理由

1. **Go 原生 LLM 框架**：LangChain 的 Go 生态不成熟，Eino 是 Go 原生实现的 LLM 编排框架
2. **类型安全**：相比 Python LangChain，Eino 利用 Go 类型系统提供编译期检查
3. **流式支持**：原生支持流式 LLM 调用，直接输出到 gRPC Server Streaming
4. **组件化**：Chain/Graph 抽象、Prompt Template、Output Parser 等开箱即用
5. **中国生态**：对 DeepSeek、通义千问等国产模型有更好的兼容性

---

## 五、向量数据库：Chromem-go

### 决策

选择 **Chromem-go** 作为嵌入式向量数据库。

### 备选方案对比

| 特性 | Chromem-go（选用） | Milvus | Qdrant | PGVector |
|------|-------------------|--------|--------|----------|
| **部署方式** | 嵌入式（Go 库） | 独立服务 | 独立服务 | PostgreSQL 插件 |
| **运维成本** | 零 | 高 | 高 | 中 |
| **性能** | 中（内存检索） | 极高 | 极高 | 高 |
| **持久化** | 文件（bolt） | 支持 | 支持 | 支持 |
| **Go SDK** | 原生 | 需 gRPC | 需 gRPC | 需 go-pg |

### 理由

1. **零运维**：嵌入式库，无需额外部署向量数据库服务，适合中小规模知识库
2. **Go 原生**：直接作为库引入，无需 gRPC 客户端，集成简单
3. **足够性能**：对于个人/团队知识库（文章数 <10 万），内存检索足够
4. **未来可升级**：可扩展性要求提升时，可无缝切换为 Milvus/Qdrant（接口一致）

### 风险

- 单机部署，不支持分布式
- 数据量增长后检索性能下降

---

## 六、ORM 框架：GORM

### 决策

选择 **GORM** 作为数据库 ORM 框架。

### 理由

1. **Go 生态最流行**：社区最大、文档最全、问题解决方案最多
2. **AutoMigrate**：开发阶段自动同步表结构，提升迭代效率
3. **Hook 机制**：`BeforeCreate` 中生成 xid 主键，代码简洁
4. **软删除**：内置 `gorm.DeletedAt` 支持，无需手动实现

### 约定

- 外键约束在数据库层面不设置，保持逻辑引用（通过 `user_id`、`repo_id` 等字段）
- 禁止 JOIN 查询，多表数据在 service 层组合
- 使用 `slog-gorm` 适配器统一日志

---

## 七、数据库：MySQL

### 决策

选择 **MySQL 8.0+** 作为关系型数据库。

### 理由

1. **成熟稳定**：经过大规模验证的关系型数据库
2. **JSON 支持**：MySQL 5.7+ 的 JSON 类型可用于存储非结构化数据（如消息的 `extra` 字段）
3. **生态友好**：GORM 对 MySQL 支持最好
4. **运维成本低**：团队对 MySQL 最熟悉

---

## 八、认证方案：JWT (RSA-2048)

### 决策

采用 **RSA-2048 签名 JWT** 实现认证，Access Token（15 分钟） + Refresh Token（30 天）双令牌机制。

### 理由

1. **无状态认证**：网关无需查询数据库即可验证用户身份，减少延迟
2. **RSA 非对称签名**：user-server 持有私钥签发，gateway/chat-server 仅持公钥验证，私钥不外泄
3. **双令牌机制**：短期 access token 减少泄漏风险，refresh token 提供良好用户体验
4. **服务间认证**：内部服务使用共享密钥（Service Token）认证，独立于用户认证体系

---

## 九、配置管理：Viper

### 决策

采用 **Viper** 管理配置，支持 YAML 文件 + 环境变量覆盖。

### 配置层级

1. 默认值（代码中设置）
2. 配置文件（`config.yaml`）
3. 环境变量（`KNOWSYNC_{SERVER_NAME}_*`）

### 理由

1. **自动解析**：`AutomaticEnv()` + `Unmarshal()` 自动映射环境变量到结构体
2. **多源支持**：文件、环境变量、远程配置中心可同时使用
3. **项目中已熟用**：各服务均已有标准的 Viper 配置实现

---

## 十、前端框架：React 19 + TypeScript + Vite

### 决策

前端选用 **React 19 + TypeScript + Vite + Tailwind CSS**，通过 Caddy 反向代理部署。

### 理由

1. **React 19**：最新稳定版，Server Components、Actions 等新特性提升开发体验
2. **Vite**：极快的 HMR 开发体验
3. **Tailwind CSS**：原子化 CSS，开发效率高，构建产物小
4. **Caddy**：自动 HTTPS，配置简单，适合静态文件服务 + 反向代理

---

## 十一、日志方案：标准库 slog

### 决策

使用 Go 1.21+ 标准库 **log/slog** 作为日志框架。

### 理由

1. **零依赖**：标准库自带，减少外部依赖
2. **结构化日志**：内置 JSON 格式输出，便于日志收集系统（Loki、ELK）消费
3. **性能**：零分配日志路径，性能优于 zap/zerolog
4. **兼容性**：GORM、Redis 等库均可通过适配器集成 slog

---

## 十二、ID 生成策略

### 决策

用户 ID 使用 **自增数字** 转为字符串，其他实体使用 **xid**（20 字符，全局唯一，按时间排序）。

### 理由

1. **用户 ID 数字**：用户量级有限，数字 ID 可读性高、存储友好
2. **xid**：无需中心化发号器，全局唯一，天生按时间排序（适合作为分页游标），20 字符长度合理
3. **其他实体**（会话、消息、仓库等）量级可能很大，xid 可保证分布式环境下的唯一性

---

## 十三、部署方案：Docker Compose

### 决策

使用 **Docker Compose** 编排所有服务，配合 `.env` 文件管理环境变量。

### 架构

```yaml
services:
  mysql:8.0        # 关系型数据库
  redis:7          # 缓存与消息队列
  user-server:     # gRPC :50051
  repo-server:     # gRPC :50052
  ai-server:       # gRPC :50053
  chat-server:     # gRPC :50054, WebSocket :50055
  gateway:         # HTTP :8080
  web:             # Caddy :80/:443
```

### 理由

1. **开发/生产环境一致**：避免"在我机器上能跑"的问题
2. **一键部署**：`docker compose up -d` 启动全部服务
3. **网络隔离**：内部网络 `knowsync-net` 隔离服务间通信，仅暴露必要端口
